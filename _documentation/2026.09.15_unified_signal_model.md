# Unified Signal Model — architecture and invariants

**Status:** implemented, not yet rendered by any UI surface
**Date:** 2026.09.15
**Applies to:** `src/shared/unifiedSignal.ts` and the modules listed below
**Related:** `docs/quant-v3/02` (chart workspace that should consume this), `docs/quant-v3/05` (QRM research track)

---

## 1. The problem this solves

Signal Engine V2 produces four independent scales for one symbol:

| Field | Range |
| --- | --- |
| `decision` | `buy-candidate` / `short-candidate` / `wait` / `no-trade` / `invalidated` |
| `setupQuality` | 0–100 |
| `setupType` | 12 values |
| `regime` | 8 values |

Nothing reconciles them, so each surface reconciles them itself — and that is
how a panel ends up showing `no-trade` beside `quality 88/100` beside
`breakout`. Three true statements that read as a contradiction.

The unified model resolves all of it to **exactly one of three words**, plus an
evidence list that explains that word. `SignalCoreEvaluation` is unchanged and
still carries the raw decision for the AI harness, the decision journal, and the
historical replay. What changed is that surfaces now have one thing to render.

```text
SignalCoreEvaluation (raw, authoritative, unchanged)
        +  raw factors + readings          (signalFactors.ts)
        +  price acceptance                (volumeProfile.ts)
        +  optional relative strength
        +  optional market pulse score
                  ↓
        evidence categories                (signalEvidenceAggregator.ts)
                  ↓
        gates → conclusion + strength      (unifiedSignalResolver.ts)
                  ↓
        ≤2 reasons for the collapsed card  (signalReasonPrioritizer.ts)
                  ↓
        UnifiedSignalSummary               → SignalDeskResult.unified
```

## 2. Module map

| Module | Responsibility |
| --- | --- |
| `indicators.ts` | Wilder ATR/RSI, EMA, MACD. Series-returning and index-aligned. |
| `signalFactors.ts` | Raw scored factors + `SignalReadings` from candles. |
| `volumeProfile.ts` | Estimated volume-at-price, value area, Price Acceptance state machine. |
| `unifiedSignal.ts` | The vocabulary, the object model, and all user-facing copy. |
| `signalEvidenceAggregator.ts` | Consolidates raw factors into the stable category set. |
| `signalReasonPrioritizer.ts` | Picks the at most two reasons a collapsed row may show. |
| `unifiedSignalResolver.ts` | The single place a conclusion is decided. |

Ported from the Quantactic iOS engine (`QuantApp/Sources/Signals/`). Copy was
taken from the `en` values in `QuantApp/Resources/Localization/Localizable.xcstrings`
rather than rewritten, so wording drift between the two apps stays diffable.

## 3. Invariants

These are the properties the tests in `scripts/test-unified-signal.mjs` exist to
protect. Breaking one is a defect even if nothing throws.

### 3.1 One conclusion, three words

`UnifiedSignal` is `'buy' | 'wait' | 'sell'`. No surface may invent a fourth
state or display a raw `decision` beside a unified one. Two labels that appear
to disagree are worse than one label that is honest about being unresolved,
which is what `wait` is for.

### 3.2 Lean and state are two different readings

Every piece of evidence carries both:

- **`lean`** — what price is doing: `bullish` / `mixed` / `bearish`. Independent
  of any conclusion.
- **`state`** — whether that supports the conclusion being shown: `supports` /
  `mixed` / `weakens`.

A downtrend has `lean: 'bearish'` always, and `state: 'supports'` under a SELL
setup. The displayed sentence keys on **lean**, never on state, so a SELL card
reads *"Price is holding below a key area"* and not the inverse.

Getting this wrong produces a card whose badge and sentence contradict each
other, which is the exact failure the split exists to prevent.

### 3.3 "Unavailable" is not a direction

`EvidenceAvailability` is separate from `state` so that *"we could not measure
this"* can never masquerade as a directional reading, and so no fourth badge
word enters the vocabulary. An unmeasured category shows `mixed` with
`availability: 'unavailable'` and is excluded from reason selection.

### 3.4 The category list does not grow with the indicator list

Categories are fixed: `trend`, `momentum`, `volume`, `price-acceptance`,
`relative-strength`, `market-context`, and the `risk-plan` gate. A new momentum
indicator makes the Momentum row **better informed**, not the screen longer.

`evidenceCategoryFor()` is exhaustive with no `default`: adding a
`SignalFactorKind` fails to compile until someone decides which row absorbs it.
A scored factor that reaches no category is worse than no factor, because it can
drive the conclusion while being invisible in the list the user is told is
complete.

### 3.5 Factor polarity comes from the kind, not the flag

`SignalFactor.positive` means *"this condition was detected and scored"*, **not**
*"this is bullish"*. A lost moving average is recorded with `positive: true`.
Polarity therefore comes from `factorPriceLean(kind, positive)`, which consults
the flag only for `rsi` and `price-move` — the two kinds where the detection
rules do set it to mean direction.

This is inherited from the iOS engine and is the single most likely thing for a
future reader to get wrong.

### 3.6 The risk plan is a gate, not a direction

`risk-plan` is deliberately **not** in the evidence array. It has no direction,
so including it meant inventing a Supports/Mixed value for it and asking every
reader to remember to filter it back out. It travels as
`UnifiedSignalSummary.riskPlan` instead.

### 3.7 A score can never promote a WAIT

The conclusion is decided by gates, in order:

1. Insufficient history → `wait` (`wait-data`)
2. Blocking corporate event → `wait` (`wait-event-risk`)
3. No usable risk plan → `wait` (`wait-risk`) — **whatever the setup quality**
4. Trigger not confirmed → `wait` (`wait-unconfirmed`)
5. Two categories contradict, or price is rejected where it matters → `wait` (`wait-mixed`)

`setupQuality 97` with `positionSize 0` is a `WAIT`. Strength is then capped at
**74** for a `wait` and floored at **55** for a decided conclusion, so the number
can rank clarity *inside* a conclusion but can never contradict the word beside
it.

### 3.8 A SELL never carries long geometry

If the resolver reaches `sell` and the risk plan is not short-side, the plan is
dropped to `null` rather than shown. A short conclusion beside long entry/stop
levels is actively dangerous, not merely untidy.

### 3.9 Strength is not a probability

`strength` is 0–100 clarity of evidence: agreement + confirmation + data
quality, less a conflict penalty. It is **never** rendered with a percent sign.
`strengthLabel()` centralises the phrasing (`"Signal strength 84/100"`) so no
surface can quietly turn it back into a percentage.

## 4. Price Acceptance

Quant previously had no concept of acceptance, which is why one bar poking
through the prior high could set the whole conclusion.

**Profile construction.** Each bar's volume is spread across the price range it
actually traded through, proportional to overlap. Assigning a bar's whole volume
to its closing price is what makes naive profiles a picture of *closes* instead
of a picture of *participation*. From that: point of control (heaviest bin, ties
to the lower bin) and a 70% value area expanded outward from the POC always
taking the heavier neighbour, contiguous by construction.

**Acceptance requires all three**, not any one:

1. `requiredCloses: 2` completed closes beyond the boundary — one tick through a
   level is noise;
2. `minimumAtrDistance: 0.15` ATR beyond it — so a level price is merely resting
   on does not count;
3. `minimumRelativeVolume: 1.10` — a move nobody traded is not acceptance.

**Honesty constraints.** `isApproximation` is always `true` and is carried
through to the advanced facts: this is built from OHLCV bars, not exchange tick
data, so nothing downstream may describe it as true volume-at-price. An
unmeasurable profile returns `state: 'unavailable'` with `null` levels rather
than a fabricated neutral reading.

**Only completed candles count.** `completedCandles()` drops an in-progress bar,
inferring the interval from the last two timestamps. This is what stops a
conclusion from flapping inside a single bar.

### The asymmetry in the gates

`upsideConfirmed` and `downsideConfirmed` are **not** mirror images, on purpose.

The core engine has real long triggers (breakout, MA reclaim, pullback
continuation). It has no acceptance-based *breakdown* trigger, and inventing a
symmetric one out of "trend and momentum agree" would let a slow drift read as a
confirmed breakdown. So the downside gate requires the one real bearish
confirmation available: measured acceptance *below* value, with the symbol's own
trend or momentum behind it. When acceptance cannot be measured the answer is
`wait`, not a guess — which is why a scan with no usable volume history never
reaches SELL.

A genuinely symmetric bearish engine is a larger piece of work: mirrored
detection rules, a direction-neutral trigger state machine, and short-side risk
geometry. Until that exists this gate stays narrow, and the narrowness is
documented rather than hidden.

## 5. The bug this port exposed

`classifySetup` could **never** return `breakout`. Proof:

`nearestResistance` returned the nearest pivot high *above* the close, else fell
back to `max(high)` over the trailing 20 bars **including the bar being
evaluated**.

- If a pivot high above the close exists, then `resistance > close`, so
  `close > resistance` is false.
- Otherwise the fallback is `max(high)` over a window containing the current
  bar, so `resistance >= current.high >= current.close`, and `close > resistance`
  is false again.

Both branches are unsatisfiable, so the `breakout` arm was dead code. Two
further consequences:

- `distanceToResistancePercent` reported a fraction of a percent on every push
  to a new high (the bar's own high sits just above its close), so
  `evaluateSignalCore` pushed *"Price is too close to resistance for a long
  trade"* and downgraded real breakouts to `no-trade`.
- `retest-entry` (`|close − resistance| < 0.45 ATR`) was almost always true under
  the fallback, so it absorbed the misclassified cases and the engine
  over-produced it.

**Fix.** Structure levels come from closed bars only:

```ts
swingHigh(candles, lookback = 20, offset = 1)  // offset 1 excludes the forming bar
swingLow(candles, lookback = 20, offset = 1)
```

`nearestSupport` / `nearestResistance` now return `null` when price has cleared
every level in the window. `null` is the meaningful answer — it means open air
overhead, which is different from "resistance a hair above the close". Callers
already handled `null` for these fields, and `buildRiskPlan`'s `??` fallbacks
now produce sane ATR-derived targets instead of self-referential ones.

`classifySetup` derives `breakout` from `swingHigh(candles, 20, 1)` and
`failed-breakout` from `swingHigh(candles, 20, 2)` — the latter needs a window
excluding both the current and previous bar, so that `prev.high > level` can
express "price poked above and came back".

Guarded by Test 9 in `scripts/test-unified-signal.mjs`, which asserts both the
setup classification and the absence of the bogus blocker.

## 6. Relationship to QRM-3

Per `docs/quant-v3/05`, three models coexist and are **not** merged:

| Model | Speaks in | Authority |
| --- | --- | --- |
| Signal Engine V2 + unified model | `BUY` / `WAIT` / `SELL` | Authoritative |
| QRM-3 (`qrmDecision.ts`) | `long-candidate` / `short-candidate` / `wait` / `unavailable` | **Experimental only** |
| Kronos (`kronosDistribution.ts`) | "sampled median positive" | Descriptive |

Each keeps its native semantics — `ResearchModelView` deliberately has no shared
numeric `confidence` field. When they disagree,
`describeModelDisagreement()` returns *"Models disagree — investigate
assumptions"*; that disagreement is research context, not something to average
until a consensus appears.

QRM's own forecast pipeline (point-in-time feature builder, analogue weighting,
stationary block bootstrap) is separate work. `kronosDistribution.ts` exists so
the decision functional has a real distribution to read in the meantime, and it
is labelled as Kronos throughout — never as QRM.

## 7. Extending this safely

**Adding an indicator.** Add the `SignalFactorKind`, give it a polarity in
`factorPriceLean`, and map it in `evidenceCategoryFor`. The compiler will refuse
until both are done. Do not add a category.

**Adding a category.** Add it to `SignalEvidenceCategory`, then to
`CATEGORY_TITLES`, `CATEGORY_SHORT_MEANINGS`, `CATEGORY_EXPANDED_MEANINGS`,
`CATEGORY_LEAN_SENTENCES`, `CATEGORY_WATCH_LINES`, and the priority arrays in
`signalReasonPrioritizer.ts` and `unifiedSignalResolver.ts`. Consider hard
whether an existing row could absorb the evidence instead — see invariant 3.4.

**Changing a threshold.** Thresholds live at the top of their module as named
constants. Changing one is a model change: bump
`UNIFIED_SIGNAL_MODEL_VERSION`, which is part of the Signal Desk cache key, so
cached conclusions from the old resolver are invalidated.

**Adding copy.** All user-facing strings live in `unifiedSignal.ts`. A sentence
inlined at a call site is a bug: it cannot be reviewed for tone, and it drifts
from the iOS wording silently.
